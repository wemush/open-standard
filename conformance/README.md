# WOLS Conformance Test Vectors

Shared, language-neutral test cases that every WOLS implementation should pass. They target **WOLS 1.5.0**: the 1.3.0 wire format, which later versions don't change, the 1.4.0 signature scheme and numeric `generation` tolerance, the 1.5 data model, and the 1.5 compact URL rules. Each file's `wolsVersion` is the version that defines its cases: `1.3.0` for the wire-format files, `1.4.0` for `signatures.json`, and `1.5.0-rc.2` for `data-model.json`, `bundle.json`, `compact.json` and `compact-signatures.json` (the final 1.5.0 release changed none of their cases). Cases added later to an older file are marked in their descriptions. An implementation of 1.4.x passes every file except the four 1.5 files. See [SPECIFICATION.md](../SPECIFICATION.md).

| [`vectors/data-model.json`](./vectors/data-model.json) | 1.5 label members (`taxon`, `form`, `derivedFrom`, `condition`, `container`, `lot`, `strain.accession`), optional members, `version` syntax, keeping unknown members, `_meta` casing (1.5.0-rc.1) | `validate`, `roundtrip` |

## Case format

Every file has this shape:

```json
{
  "wolsVersion": "1.3.0",
  "description": "…",
  "specSection": "…",
  "cases": [
    {
      "id": "stable-case-id",
      "operation": "validate | create | roundtrip | validateBundle | parseCompact | derive | decrypt | decryptFields | sign | verify | unwrap | loadKeySet | verifyNested",
      "requirement": "MUST | SHOULD",
      "description": "…",
      "input": { },
      "expected": { }
    }
  ]
}
```

What `expected` means for each operation:

- **`validate`**: The input is a specimen object.
  - `valid` is the required outcome.
  - `errorField`, when present, names the field that must be reported.
  - `warningField`, when present, names a field that should produce a warning without failing validation.
  - Field names are dot paths, with array positions as decimal segments: `strain.lineage`, `container.capacity.unit`, `derivedFrom.0.id`. A missing required member is reported on its own path (`taxon.scientificName`, not `taxon`).
- **`roundtrip`** (1.5.0-rc.1): The input is `{ text }`, a serialized label. Decode it with the implementation's normal decoder, encode it again, and parse the result. It must equal `output` as a JSON value; member order doesn't matter.
- **`validateBundle`** (1.5.0-rc.1): The input is a Bundle. `valid` and `errorField` work as for `validate`, with paths from the bundle root (`observations.0.specimen`). Only implementations that support Bundles need to run these cases.
- **`parseCompact`** (1.5.0-rc.2): The input is `{ url }`, a compact URL. Parse it with the implementation's compact URL decoder.
  - On success, `label` is what the URL decodes to: `id` with the `wemush:` prefix, `species` as a scientific name, and `type`, `stage`, `created` (RFC 3339 UTC), `batch` and `strain` (`name`, `generation`, `transferDepth`) when present. `unrecognized`, when present, holds every unregistered parameter by name with its decoded value, and `sig` the reserved `sig` value, kept and not verified. Compare it as a JSON value; implementations that expose a different shape map their result onto it. Implementations that don't expose unregistered parameters can skip the `unrecognized` comparison.
  - `warningField`, when present, names the parameter that should produce a warning (`s` for a legacy species code, `td` for a malformed transfer depth). When it's absent, no warning is expected.
  - On failure, `refused` is `true` and `reason` is a suggested category from the table below, plus `unsupported-version` (a version segment other than `v1`), `encrypted-url` (an encrypted URL given to the compact decoder) and `duplicate-parameter`.
- **`create`**: The input is the argument to the implementation's specimen factory. Check the resulting `type` and `stage` (`null` means no stage), and whether a `warning` was emitted.
- **`derive`**: PBKDF2-HMAC-SHA256 intermediate value, provided for debugging key derivation.
- **`decrypt`**: The input is an encrypted URL plus a `secret`, which is either `{ kdf: "pbkdf2", passphrase }` or `{ kdf: "raw", keyBase64url }`.
  - On success, the decrypted bytes must equal `plaintext` exactly and parse to `specimen`. `specimen` is the decoded label: where the plaintext has a JSON integer `strain.generation`, it holds the decimal string (see [Numeric `generation`](#numeric-generation-140)).
  - `sig` and `sigVerified`, when present, check the reserved `sig` parameter. The decoder must keep `sig` with the decoded label, equal to this value, and must not report it as verified. `sigVerified` is always `false`, because decoding never verifies; verification is the separate `verify` operation. Implementations that don't expose URL parameters can check only that decryption succeeds.
  - On failure, decryption must be refused. `reason` is a suggested error category and doesn't have to match exactly.
- **Suggested `reason` values**:

  | Reason | Meaning |
  | ------ | ------- |
  | `invalid-url` | Not an encrypted URL |
  | `invalid-encoding` | Malformed percent-encoding, or a decoded value that is not valid UTF-8 |
  | `missing-parameter` | A required parameter is absent |
  | `unexpected-parameter` | A parameter appears where it's forbidden |
  | `invalid-parameter` | A parameter is malformed (for example, `i` that isn't plain decimal digits) |
  | `legacy-format` | A URL or field object without `kdf` (pre-1.3.0) |
  | `unsupported-kdf` | Unknown `kdf` value |
  | `insufficient-iterations` | Fewer than 10,000 PBKDF2 iterations |
  | `excessive-iterations` | More than 10,000,000 PBKDF2 iterations, alone or in total |
  | `invalid-key` | Wrong key length |
  | `authentication-failed` | AES-GCM authentication failed |
  | `invalid-plaintext` | The plaintext has a byte order mark or isn't valid JSON |
  | `id-mismatch` | The decrypted `id` doesn't match the URL |
  | `identifying-field` | An identifying field is encrypted |

- **`decryptFields`**: The input is an embedded label whose fields may hold field-level encryption objects, plus a `secret` in the same form as `decrypt`.
  - On success, decrypting every encrypted field must produce `specimen`.
  - On failure, the label must be refused, with `reason` as for `decrypt`.

### Signatures (`signatures.json`, 1.4.0)

`signatures.json` has the usual fields, with `wolsVersion` set to `"1.4.0"`, plus three more at the top level:

```json
{
  "wolsVersion": "1.4.0",
  "signingDomain": "WOLS-SIG-v1",
  "testKeys": {
    "mushoh-2026": { "seedBase64url": "…", "publicKeyBase64url": "…", "trusted": true },
    "acme-lab-1":  { "seedBase64url": "…", "publicKeyBase64url": "…", "trusted": true },
    "attacker-1":  { "seedBase64url": "…", "publicKeyBase64url": "…", "trusted": false }
  },
  "trustStore": {
    "mushoh-2026":  { "alg": "Ed25519", "publicKeyBase64url": "…" },
    "mushoh-alias": { "alg": "Ed25519", "publicKeyBase64url": "…" },
    "acme-lab-1":   { "alg": "Ed25519", "publicKeyBase64url": "…" }
  },
  "cases": [ ]
}
```

- **`testKeys`**: Ed25519 key pairs keyed by name. The seed is the 32-byte RFC 8032 private key; the public key is the 32-byte encoded point. Both are base64url without padding. Each seed is the SHA-256 of `WOLS 1.4.0 conformance test key: {name}`. These keys are public: **never use them for real labels.**
- **`trustStore`**: The trust store that every `verify` case uses, mapping kid to key. `mushoh-alias` is a second kid for the `mushoh-2026` key, so the vectors can check that the kid is signed. `attacker-1` is deliberately absent. `compact-signatures.json` carries the same keys and the same trust store, plus the short kid `w1`, a third kid for the `mushoh-2026` key.
- **`signingDomain`**: The first line of every signing input.

Each case's `input.form` is `"embedded"` or `"encrypted-url"`. Embedded labels are given as **JSON text** in `input.label`, exactly as a scanner would read it. Parse that text yourself: several cases depend on how the text is spelled, such as escapes, number spellings, member order, and lone surrogates. Encrypted URLs are given in `input.url`.

- **`sign`**: Input is `{ form, label | url, kid, key }`. `form` is `embedded`, `encrypted-url` or (from 1.5.0) `compact-url`; for a URL form, `expected.url` is the signed URL. `key` names an entry in `testKeys`; sign with its seed, and put `kid` in the token.
  - `expected.signingInput` is the exact signing input, as a string. Encode it as UTF-8 to get the bytes Ed25519 signs. Compare it first when debugging.
  - `expected.signature` is the exact token, `{kid}.{base64url signature}`. Ed25519 is deterministic, so it must match byte for byte.
  - For `encrypted-url`, `expected.url` is the signed URL: `input.url` + `&sig=` + token.
  - For `embedded`, put the token in the label's top-level `signature` member. Member position isn't checked.
  - `sign-embedded-replaces-signature` gives a label that already has a `signature`. The signer ignores it, so the token is the same as for `sign-embedded`.
  - The `sign-jcs-*` cases exercise RFC 8785 member ordering, string escaping, and number formatting. Their `signingInput` shows the canonical form.
  - **Refusals**: When `expected` is `{ "refused": true }`, the signer must refuse and produce no signature. Report it however the library reports errors (a thrown error, an error result); only the refusal is checked. The `sign-refuse-*` cases cover a URL with no query, a URL with an empty query, an already-signed URL, and label text that isn't I-JSON.
- **`verify`**: Input is `{ form, label | url }`, plus an optional `trustStore`. Verify against `input.trustStore` when it is present, and against the file's `trustStore` otherwise. `form` is the form a single-string verifier detects ([Choosing the form](../SPECIFICATION.md#verification-result)): in `compact-signatures.json`, a URL that isn't a signable compact URL (two path segments, `WEMUSH://`, `web+wemush://`) has the form `encrypted-url`, and is `malformed` because it carries `sig`.
  - `input.form` is explicit, but it always agrees with the rule for a single string input: text that starts with a URI scheme (`[A-Za-z][A-Za-z0-9+.-]*:`) is a URL, and anything else is embedded label JSON. A library with one string entry point must reach the same status by detecting the form.
  - `expected.status` is one of `valid`, `invalid`, `unknown-kid`, `malformed`, `unsigned`, and must match exactly.
  - When the status is `valid`, `expected.kid` is the kid to report. `expected.signingInput` is the input that verified, for debugging.
  - Statuses are checked in a fixed order: parse the embedded label text as I-JSON (`malformed`, signed or not), then `unsigned`, then the token and URL rules (`malformed`), then the trust store lookup (`unknown-kid`), then the signature (`invalid` or `valid`). So a case that breaks several rules has exactly one correct status.
  - **Unusable trust-store entries**: The `verify-trust-store-*` cases supply an `input.trustStore` whose only entry has an off-curve key, a 31-byte key, or the algorithm `Ed448`, and they set `expected.configError: true`. The expected status is `invalid`. An implementation that rejects the entry when the trust store is built, as the specification recommends, also passes, provided it reports that rejection as a configuration error. `configError` is a marker for test harnesses, not part of the verification result.
- **`loadKeySet`**: Build a trust store from a key set document (the `/.well-known/wols-keys.json` shape), then verify with it. `input.keySet` is the document as a JSON value, which isn't always an object.
  - When `expected` is `{ "configError": true }`, loading must fail as a configuration error, however the library reports one. The whole document fails, not just the bad entry: every failing document that has entries also has a good one. These cases cover a damaged `Ed25519` entry (an off-curve, short, long, padded, or non-canonical key, a missing or non-string key, a missing, invalid, or non-string kid), a duplicate kid among usable entries, and a document or entry with the wrong shape (not an object with a `keys` array, a `keys` element that isn't an object, or an entry without a string `alg`).
  - Otherwise loading must succeed. `expected.kids` lists the kids in the resulting trust store, sorted by code unit. `expected.skipped` counts the entries skipped because their `alg` isn't supported. Reporting skipped entries is optional, so a library that doesn't report them checks only `kids`.
  - Then verify `input.label` (always `form: "embedded"`) against the loaded store. `expected.status` and, for `valid`, `expected.kid` are checked as for `verify`.
  - Entries whose `alg` isn't `Ed25519` (including `ed25519`: the comparison is exact) are skipped without checking their other members, and a skipped entry may share a kid with a usable one. A kid whose only entry was skipped verifies as `unknown-kid`.
  - These rules apply only to key set documents. A trust store the caller builds directly still treats a non-`Ed25519` entry as a configuration error, as the `verify-trust-store-wrong-alg` case shows.
- **`unwrap`** (1.5.0-rc.2, `SHOULD`): The optional step before compact URL verification. Input is `{ text }`; `expected.url` is the `wemush://v1/` URL it unwraps to, or `null` when it doesn't unwrap. Every non-null result is a signed URL from the same file and must verify as `valid`. Only implementations that provide the unwrap step need to run these cases.
- **`verifyNested`**: Sign-then-encrypt (see [Plaintext or ciphertext](../SPECIFICATION.md#plaintext-or-ciphertext)). The plaintext of an encrypted URL is an embedded label, which may carry its own `signature`, and the URL may carry `sig` as well. Input is `{ form: "encrypted-url", url, secret }`, with `secret` as for `decrypt`. Verify against the file's `trustStore`. Run three steps, each checked on its own:
  1. **Outer**: Verify `input.url` as an encrypted URL. `expected.outer` is checked as `expected` is for `verify`: `status`, and for `valid`, `kid` and `signingInput`. Don't let this step depend on decryption: a scanner can verify before it spends PBKDF2 work.
  2. **Decrypt**: Decrypt `input.url` with `secret`. `expected.decrypt` is `{ success: true, plaintext }`, where the decrypted bytes must equal `plaintext` exactly, or `{ success: false, reason }`, as for `decrypt`.
  3. **Inner**: When decryption succeeds, verify the decrypted text as embedded label JSON, exactly as decrypted, not a label the library rebuilt from it. `expected.inner` is checked like `expected.outer`. It is absent when decryption fails.

  The outer and inner statuses are independent: either can be `valid` while the other isn't. `nested-valid` is the `sign-embedded` label and token, encrypted with the fixed salt, IV, and iteration count of `encrypted.json`, and then signed as a URL under `acme-lab-1`; `sign-nested-encrypted-url` is that last signing step as an ordinary `sign` case. The other cases cover an unsigned plaintext (`nested-inner-unsigned`), a changed `i` that breaks both the outer signature and decryption (`nested-tampered-iterations`), a re-encryption that breaks only the outer signature (`nested-reencrypted`), a label changed after it was signed (`nested-inner-tampered`), and the inner `embedded` token copied into `sig`, which fails because of domain separation (`nested-inner-token-as-outer-sig`).

To implement `signSpecimen` and `verifySpecimen` from this file:

1. **Signing input**: `"WOLS-SIG-v1\n" + form + "\n" + kid + "\n"` followed by the body.
2. **Embedded body**: First parse the label text as an I-JSON object. It is `malformed`, signed or not, if it isn't JSON, isn't an object, has duplicate member names in any object (compared after unescaping; `JSON.parse` and Python's `json.loads` silently keep the last one, so detect them separately), has a lone surrogate, or has a non-finite or overflowing number (`NaN`, `Infinity`, `1e400`). Then, if there's no top-level `signature`, it is `unsigned`. Otherwise remove only the top-level `signature`, and produce the RFC 8785 (JCS) canonical form, encoded as UTF-8.
3. **URL body**: The URL up to, but not including, its final `&sig=…` parameter, byte for byte, with nothing decoded or re-encoded. A URL without a parameter named exactly `sig` is `unsigned`. The URL is `malformed` if any of these hold:
   - `sig` is not the last parameter, or appears more than once.
   - The URL has a fragment.
   - The URL has a character outside `!` through `~`.
   - The URL doesn't start with `wemush://v1/encrypted/`.
4. **Token**: Matches `^[A-Za-z0-9_-]{1,64}\.[A-Za-z0-9_-]{86}$`, and the signature part decodes to 64 bytes whose base64url re-encoding is identical (the unused bits are zero). Anything else is `malformed`.
5. **Kid**: Not in the trust store means `unknown-kid`. Never fall back to a key in the label: the `*-untrusted-*` cases carry an attacker's `publicKey` in the label. A kid whose entry is unusable (not `Ed25519`, not 32 bytes, or not a curve point) gives `invalid`.
6. **Signature**: Ed25519 verification (RFC 8032 §5.1.7, rejecting `S ≥ L`) gives `valid` or `invalid`.

Signed labels must also keep decoding. `encrypted.json` has `decrypt-signed-url` and `embedded.json` has `signed-label-valid`. A 1.3.x decoder passes both, because it treats the token as the reserved value it preserves.

A case marked `SHOULD` is recommended behavior. An implementation that skips it can still conform.

> **Fixed salts and IVs**: The encrypted vectors use fixed salts and IVs so the output is reproducible. Real generators **MUST** use fresh random values.

### Numeric `generation` (1.4.0)

`strain.generation` is a string, but the Python `wols` 1.3.0 library wrote it as a JSON integer. Decoders SHOULD read such a value as its decimal string, with a warning (see [Generation Notation](../SPECIFICATION.md#generation-notation-v120)). Three `SHOULD` cases cover it:

| Case | File | Expected |
| ---- | ---- | -------- |
| `generation-numeric` | `generation.json` | Valid, with a warning on `strain.generation` |
| `decrypt-numeric-generation` | `encrypted.json` | Decrypts; `plaintext` keeps the integer, `specimen` has `"generation": "1"` |
| `decrypt-fields-numeric-generation` | `field-encryption.json` | Decrypts; `specimen` has `"generation": "1"` |

### Schema sync (1.5.0-rc.1)

From 1.5.0-rc.1 the [JSON Schema](../schema/1.5/) is normative. Every `validate` and `validateBundle` input gets the same verdict and error field from the schema plus the two rules JSON Schema can't express (`strain.lineage` equal to `derivedFrom[0].id`, and bundle references that resolve). [`tools/validate_schema.py`](./tools/validate_schema.py) checks this, and also that every `roundtrip` output is a valid label. Reference libraries MUST run the same check in their own tests (see [Schema and Data Model](../SPECIFICATION.md#schema-and-data-model-v150)).

## Checksums

[`vectors/SHA256SUMS`](./vectors/SHA256SUMS) lists the SHA-256 hash of every vector file, in `sha256sum` format. Implementations that vendor the vectors can check what they copied with `sha256sum -c SHA256SUMS`. The generator rewrites the file, and the verifier checks it.

## Tools

```bash
# Regenerate the vectors (deterministic)
pip install "cryptography>=42"
python conformance/tools/generate_vectors.py

# Check every vector against an independent implementation of the spec (Node.js 20+, no dependencies)
node conformance/tools/verify_vectors.mjs

# Check the validate vectors and example records against the 1.5 JSON Schema
pip install "jsonschema>=4.18"
python conformance/tools/validate_schema.py
```

`verify_vectors.mjs` implements the parts of the specification that the vectors exercise, using only WebCrypto. It is a cross-check that the vectors match the specification text, not a reference library.
